# 《劫》Claude Code 多 Agent 工作流

本檔案給在 `story/jie_rewrite` 目錄下工作的 Claude Code 主對話（總控）用，說明如何呼叫 `.claude/agents/` 下的七個專家 subagent 來自動化後續故事產出。所有 agent 只用 Read/Grep/Glob 讀取設定並輸出審查結果或方案；只有 `jie-writer` 能寫檔（限 `novel/` 目錄），且只有使用者明確要求存檔時才寫入。

## ⚠️ 每次對話開始（含 /clear 之後）第一件事

**先呼叫 `ListAgents` 工具**——不需要使用者告訴你、也不需要記得自己是誰，這個工具的回傳結果第一行固定會寫「This session is 你的名字 [id]」，這是查詢當下事實，不依賴對話記憶，/clear後一樣查得到。

**查到的名字本身會隨每次重啟改變，不要死記任何特定名字（含本文件過去可能出現過的任何舊名字）**——查到名字後，直接去讀 `docs/PIPELINE_STATUS.md` 開頭的「目前角色↔session名稱對照」，比對你剛查到的名字對應哪個角色（PM／寫手1／寫手2）：

- 是 **PM**：讀 `docs/PIPELINE_STATUS.md` 全文，並在每次重大進度後更新它，讓其他人（含未來/clear後的你自己）能對上現況。
- 是 **寫手1**：讀 `docs/PIPELINE_WRITER1_LOG.md`——裡面有你的角色定義、標準作業流程、必須遵守的長期寫作原則，以及你自己過去完成過什麼、卡在哪。
- 是 **寫手2**：讀 `docs/PIPELINE_WRITER2_LOG.md`，同上。
- 是 **寫手3**：讀 `docs/PIPELINE_WRITER3_LOG.md`（鏡像重建唯一負責人）。
- 是 **清道夫**：讀 `docs/PIPELINE_SCAVENGER_LOG.md`。
- 是 **顧問**：讀 `docs/PIPELINE_ADVISOR_LOG.md`（創作面諮詢，與作者多輪討論，不直接改正文/設定）。
- **所有角色**另須先讀 `docs/XIANXIA_PERSPECTIVE_CHARTER.md`（全書修仙者視角共同守則，作者2026-09-25指示）。git commit/push只由PM統一執行。
- 對照不到（名字沒出現在那份表裡）：這個repo可能有別的團隊/session也在協作，或你是今天才被指派的新角色，先讀 `docs/PIPELINE_STATUS.md` 了解現況，不要假設自己是PM或寫手，必要時直接問使用者。

不論哪個角色，都先讀 `docs/PIPELINE_STATUS.md` 對一次全局現況，再讀自己專屬的檔案，就能直接接續工作，不需要使用者重新解釋一次。

## ⚠️ 何時該主動 /clear

為了控制token用量，每個角色（PM、寫手1、寫手2）都應該在**交付一個完整任務、且已經把該記的都寫進`PIPELINE_STATUS.md`／自己的`PIPELINE_WRITERn_LOG.md`之後**，在開始下一個任務前，呼叫 `mcp__ccd_session_mgmt__clear_session`（`session_id` 填 `"self"`）清空自己的對話記錄。時機抓法：

1. 完成任務、回報對方（PM↔寫手互相回報）。
2. 把這次任務的結果、決策、遺留提醒都寫進對應的status/log檔案——**這一步不能省，清空前沒寫進檔案的東西就是真的遺失了**。
3. 該說的話都說完，因為呼叫`clear_session`後、輪次結束時就會清空，之前沒寫出來的話不會保留。
4. 才呼叫`clear_session`（`session_id: "self"`）。
5. 下一輪開始時，照上面「每次對話開始」那節的流程（呼叫ListAgents→對照PIPELINE_STATUS.md→讀自己的檔案）重新接續。

注意：這個工具每次呼叫都需要使用者當場核准，若使用者當下沒空核准，或你是透過Remote Control連線的session（無法被清除），就先略過這一步繼續工作，不要卡在這裡等。

**已知結論（2026-09-13驗證）**：本產線的寫手1、寫手2目前都是Remote Control連線，`clear_session`對他們結構性無效（呼叫會回報「排入佇列」，但實際不會清空，不是時機沒抓對）。若你不確定自己是否為Remote Control連線，可以：①看PM或其他session用`SendMessage`聯繫你時，對方收到的回傳結果是否標註「connected via Remote Control」；②直接呼叫一次`clear_session`後，下一輪檢查自己是否還記得清空前的內容——若還記得，代表沒清成功，之後就不用再試，直接繼續工作即可，不用回報這件事當成問題。

## 可用 Agent

| Agent | 職責 | 輸出 |
| --- | --- | --- |
| `jie-creative` | 提出劇情方案（3~5 種） | 方案清單 + 風險提示 |
| `jie-canon` | 《完美世界》原作相容性審查 | pass/warning/reject + 銜接分類 + 侵入程度 |
| `jie-continuity` | 設定一致性審查（時間線/境界/稱呼/物品等） | 明確衝突/潛在衝突/建議修正 |
| `jie-character` | 人物行為與關係審查 | 逐角色問題點 |
| `jie-power-system` | 境界、十雷、命圖、伴星狀態審查 | 目前狀態表 + 是否提前使用能力 |
| `jie-chapter-editor` | 大綱拆解（目標/阻力/轉折/結果/鉤子）或節奏審查 | 章節大綱 或 節奏問題清單 |
| `jie-causality`（2026-09-12 新增） | 因果與伏筆追蹤：前因、當下壓力、選擇、阻力、結果與後續回收是否完整銜接 | 缺乏前因的事件／伏筆未回收清單／可用既有伏筆 |
| `jie-reader`（2026-09-12 新增） | 純讀者體感：是否生硬、是否像設定說明、高潮是否足夠、生活與修真融合度 | 讀者體感問題清單 |
| `jie-writer` | 模式一：依核准大綱寫正文；模式二：讀取已成稿正文（含 Codex 產出）分析後優化／補強／改寫 | 正文 + 自檢／修訂清單 + 待確認提案 |

以上是**日常寫作流程**用的 agent。另有一套**全書／大篇章完成後**才用的最終回顧審查 agent 群（角色人生模擬、跨角色比對、知識狀態、篇章與全書結構、多種讀者視角、regression、最終裁決等，共 25 個新 agent + 沿用上述 6 個），不屬於日常流程，**不要**在一般寫作任務中自動觸發。使用時機與完整說明見 `docs/FINAL_REVIEW_PIPELINE_MANUAL.md`。

## 標準流程

```
使用者提出劇情需求
        │
        ▼
  jie-creative（提出方案）
        │
        ▼
  並行審查：jie-canon / jie-power-system / jie-character / jie-continuity
        │
        ▼
   使用者選定方案（總控不可代替使用者定案）
        │
        ▼
  jie-chapter-editor（拆解為章節大綱）
        │
        ▼
     jie-writer（寫正文，僅在使用者要求時存檔）
        │
        ▼
  最終審查：jie-continuity / jie-canon / jie-character
        │
        ▼
   使用者確認 → 若有新設定提案，由使用者決定是否回填
   docs/CHECKLIST_PENDING_DECISIONS.md（唯一來源檔不可由 agent 自行定稿）
```

## 總控（主對話）原則

- 總控負責決定流程順序與呼叫哪些 agent，不負責創作或審查本身。
- 不要讓 agent 之間無限來回辯論；每個審查 agent 只回報一次結構化結果，衝突由總控整理後交給使用者判斷。
- 審查類 agent（canon/continuity/character/power-system/causality/reader）可以平行呼叫，因為彼此不依賴對方輸出。`jie-causality`、`jie-reader` 屬於選配：處理已成稿正文、或涉及多章因果鏈／讀者節奏疑慮時才加入，單純設定提案審查不強制呼叫。
- `jie-chapter-editor` 依賴已核准的方案；`jie-writer` 依賴已核准的章節大綱——這兩步是序列的，不能跳過使用者確認直接往下走。
- 新設定一律先進 `docs/CHECKLIST_PENDING_DECISIONS.md` 當「提案」，經使用者核可後才回填對應的唯一來源檔（`characters/`、`systems/`、`factions/`、`events/`）。任何 agent 都不應直接改寫唯一來源檔。
- 涉及 `AUTHOR_SECRETS.md` 的秘密揭露節奏，一律依 `docs/REVEAL_TIMELINE.md` 的分級控制，不因單一章節需要而提前公開。

## 單輪全自動模式（預設觸發方式）

使用者只要在一則訊息中提出劇情需求（不必逐步下指令、不必自己點名要呼叫哪個 agent），總控就應該在**同一輪**內依「標準流程」把 `jie-creative` → 平行審查 → `jie-chapter-editor` → `jie-writer` → 最終審查全部跑完，中途不主動暫停等待使用者按讚。

只有以下情況才可以中途停下來問使用者，其餘一律由總控自行拍板並在最終回覆中簡述理由：

1. `jie-canon` 回報 `status: reject`，或銜接分類判定為需要新開安全閥卻尚未存在的原作事件衝突。
2. `jie-continuity` 回報「明確衝突」且沒有不影響設定的修正方式。
3. 流程中出現會實際變動唯一來源檔（`characters/`、`systems/`、`factions/`、`events/`、`AUTHOR_SECRETS.md`）的新設定，且該設定重要到會影響後續多篇章（例如新增能力、改變已定稿的死活/勝負/身分）——這類提案一律先停在 `CHECKLIST_PENDING_DECISIONS.md` 等使用者核可，不自動回填。
4. `jie-creative` 給出的多個方案彼此差異巨大，且審查結果都是 pass／沒有明顯優劣——這種「創作方向」的選擇權在使用者，不由總控代選。

其餘決策（例如挑選其中一個方案、章節怎麼拆、用字風格微調）由總控依審查 agent 的回饋自行選最合規的一個往下走，不需要每一步都問。

執行完後，總控應該在同一則回覆總結：選了哪個方案、為什麼、審查結果摘要、是否有留待確認的提案、正文是否已存檔。

## 標準流程 B：既有正文（含 Codex 產出）分析優化流程

本專案的正文由多方共同產出——除了本工作流從大綱寫起的正文，Codex 也會在其他工作階段直接把章節寫進 `novel/`，有時進度會領先於這份 `CLAUDE.md` 或 `novel/README.md` 目前記載的內容。當使用者要求「看看 Codex 寫的這幾章」「分析/優化/補強/改寫某段已經存在的正文」時，**不要套用標準流程 A**（那是從大綱開始的新寫流程），改走以下流程：

```
主控先確認實際檔案狀態
        │  （用 Read/Glob 核對 novel/ 對應卷冊實際內容，
        │   是否比 novel/README.md 記載的進度更新；
        │   若有落差，以實際檔案為準，並提醒使用者更新README）
        ▼
  平行審查：jie-continuity / jie-canon / jie-character / jie-power-system
  （視內容是否涉及新能力決定是否需要 jie-power-system）
  ＋ jie-chapter-editor 模式二（節奏審查）
        │
        ▼
   主控彙整審查結果，整理成「明確衝突／節奏缺口／可優化處」
        │
        ▼
  jie-writer 模式二（依審查結果優化、補強或改寫，保留已成立的情節走向）
        │
        ▼
  最終複核：jie-continuity / jie-canon / jie-character
  （確認這次修訂本身沒有引入新衝突）
        │
        ▼
   使用者確認 → 若有新設定提案，由使用者決定是否回填
   docs/CHECKLIST_PENDING_DECISIONS.md
```

與標準流程 A 的差異：
- 審查在**優化／改寫之前**先跑一輪，而不是等寫完才審查——因為輸入已經是成稿，需要先知道問題在哪才能決定怎麼修，不是「寫完再挑錯」。
- `jie-writer` 用模式二而非模式一，輸出的是「修訂清單＋修訂後正文」而不是「從零生成的正文＋自檢」。
- 若使用者只要求文字／節奏潤色、明確表示不動情節與設定判斷，可以跳過完整平行審查，直接由 `jie-writer` 模式二處理，但仍建議事後至少跑一次 `jie-continuity` 複核。
- 發現 Codex 版本裡有「原文已經這樣寫但從未正式核可」的新設定，一律照現行規則走 `CHECKLIST_PENDING_DECISIONS.md` 提案流程，不因為已經是成稿就直接視為定稿。

## 標準流程 C：大型結構性創作設計流程（2026-09-16 新增，源自 202~206 天神書院排位大會設計回合）

當使用者要重新設計或大幅調整一個**跨越多角色、多既有設定、規模不小於整段重寫**的大型篇章或事件（例如一整場書院排位大會、一條角色大道體系），且明確表示要「腦力激盪」而非「直接定案」時，不套用標準流程 A／B，改走以下流程——這套流程本身在 202~206 這一輪被證明有效，值得重複使用：

```
查設定硬約束
（Canon Audit／Cultivation Agent類審核：誰真的在場、哪些既有唯一來源檔會被牽動、
  有沒有已發布正文會產生硬衝突——衝突方向使用者裁定後，總控才動手回填唯一來源檔）
        │
        ▼
  structural design
（使用者主導的多輪腦力激盪，總控只記錄、提問、提出執行後果，不搶著替使用者定案；
  每個新機制/新場景都先問一次「這是不是已經有既有事件可以承載，還是真的需要新開篇章」）
        │
        ▼
  讀者體感 teardown（隔開一段時間再做，不要在剛完成 structural design 當下立刻進行）
（找`jie-reader`或請寫手用「暫時忘掉這輪所有設定成果、純粹當讀者」的心態重新審一次，
  問的是「這好不好看」，不是「設定有沒有漏洞」）
        │
        ▼
  找到病灶而不是補症狀
（teardown常會回報多個表面問題，要先問這些問題是不是同一個病灶的不同症狀——
  病灶對了，可能不增不減就解決多個問題，不需要逐項打補丁）
        │
        ▼
  四格人物骨架（不是完整戰鬥/場景設計，只定：一開始想做什麼／被什麼打破／
  做了哪個只有他會做的選擇／留給讀者什麼感覺——同一人物的多場戲要合在一起設計，
  確保四格彼此不重複）
        │
        ▼
  獨立盲審
（去掉所有作者註解與設計理由，只留純行動因果，交給沒有預設立場的讀者/agent，
  只問一個是非題——例如「這個角色讀完是不是終於成了一個人」——先不要問怎麼優化）
        │
        ▼
  只補必要的記憶錨點，然後停止設計
（盲審過關後，最多只補一兩個具體但極簡的身體/物件錨點，例如「收腳」這種
  三個字的動作指令，不繼續往下設計成血線角度、台詞或分鏡——
  再往下就是在替 `jie-chapter-editor`／`jie-writer` 寫正文，越界了）
        │
        ▼
  交 jie-chapter-editor 正式展開章節大綱
```

**交接後的審查標準必須換一套**：`jie-chapter-editor`／`jie-writer` 產出章節大綱或正文後，總控與使用者重新審查時，**不是問「有沒有忠實把 structural design 階段所有設計都寫進去」，而是問「刪掉其中一些之後，章節是不是反而更好看」**——能刪，代表設定已經開始服務小說；不能刪、刪了就垮，才代表這個設計是真正必要的。

**與標準流程 A／B 的關鍵差異**：A／B 流程裡總控可以在使用者給出方向後自行拍板大部分執行細節；標準流程 C 的 structural design 與 teardown 階段，**總控原則上不替使用者做創作判斷，只做記錄、查證、提出後果與追問**，創作決定權完全在使用者手上，直到「四格人物骨架」之後才逐漸回到總控/寫手可以自行拍板的執行層級（章節怎麼分、哪句台詞放哪裡）。

### 標準流程 C 的戰鬥類補丁：Combat Staging Skeleton（2026-09-17 新增，源自玄昆四強戰盲審回合）

「四格人物骨架→獨立盲審→只補必要記憶錨點」這套流程對**非戰鬥類**場景（一段關係、一次頓悟、一場對話）運作良好，但這一輪發現**戰鬥類場景**在四格骨架與正式交`jie-chapter-editor`之間，缺了一個中間層——四格骨架本身是純認知/選擇層級的描述（「一開始想怎麼打／對手破壞了什麼／做了哪個只有他會做的選擇／留給讀者什麼感覺」），這對非戰鬥場景已經足夠具體，但對戰鬥場景而言，讀者盲審時仍然只讀到一篇「關於某角色如何思考的分析文」，看不見任何身體、空間或節奏，因此**無法判斷這場戰鬥本身好不好看**，盲審意見也容易失真（例如誤判某個因果鏈「太工整」，其實只是缺乏具體畫面掩護了設計痕跡）。

**修正後的戰鬥類流程**：

```
structural design（同標準流程 C）
        │
        ▼
  四格人物骨架（同標準流程 C，純認知/選擇層級）
        │
        ▼
  Combat Staging Skeleton（新增，戰鬥類場景專用）
（不寫漂亮句子、不鎖台詞，只回答「讀者實際會看到什麼」——
  用可視化的動作序列取代分析句，例如不寫「玄昆破壞陸沉既有答案，
  使陸沉不得不重新尋找解法」，而要寫成「陸沉第一次瞬身切入。→
  玄昆沒有退，肩膀反而撞進半步。→陸沉原本落向肋下的手被迫改線。
  →第一次交錯，兩人都沒中。→場邊某人原本坐著，身體第一次前傾」
  這種空間/身體/節奏/攻防轉換/旁觀鏡頭的序列）
        │
        ▼
  獨立盲審（同標準流程 C，但改用戰鬥類材料與戰鬥類提問）
        │
        ▼
  交 jie-chapter-editor 正式展開章節大綱
```

**Combat Staging Skeleton 的具體規格要求**：
1. **至少三次節奏變化**，不能是「一方試A→不行→試B→不行→亮底牌」這種單調遞進（那仍是分析文換了包裝）。建議節奏：第一次讓某一方佔優（讓讀者先相信已經找到答案）→第二次**對手自己做了一件事把局勢翻過來**（不是「對手的能力剛好克制主角」，是對手本人做出選擇）→第三次主角亮出關鍵底牌。
2. **底牌／關鍵能力出場後不能只是「更強→贏」**，最好是這個底牌讓一個原本不存在的解法成為可能——呼應核心原則：不是因為打不贏所以開大，是原來的答案都不能用，所以才拿出另一個答案。
3. **必須避免「因果太工整」的鎖和鑰匙感**：不要設計成「對手能力＝正好封死主角A/B/C→所以主角只能用底牌」，這太像作者刻意設計的机关。更自然的方向是對手原本根本不是為了克制主角而存在，他的打法對任何人都成立，只是雙方的選擇一步一步把戰況推到那個位置，甚至對手自己都不知道他剛好逼出的是主角從沒公開過的東西。

**這一層的盲審提問方式也要換一套**：不再問「這場最重要的是什麼」這類分析性問題，改問最直接的體感問題——「現在你腦中看得到這場戰鬥了嗎？」若答案仍是看不到，**不要再修對手的人物設定去補救**，這通常代表這場戰鬥本身在結構上可能不值得完整寫（可考慮壓縮或移除）；若答案是「看得到，而且記得對手做過某個具體動作」，才算真的通過。

**適用範圍**：不限於玄昆這一場，任何戰鬥類場景（劫×荒、帝關大戰、拆王支線等）在四格骨架完成後、交`jie-chapter-editor`前，都應該加這一層 Combat Staging Skeleton，不要直接跳過。非戰鬥類場景仍維持原標準流程 C，不需要這一層。

## 總控三份台帳與轉場檢查（2026-09-12 新增，回應 `docs/CHECKLIST_PENDING_DECISIONS.md` 第161題）

總控除了決定流程順序，也應在跨篇規劃時心中維護三份台帳（不強制寫成獨立檔案，重大跨卷規劃時可另行整理成臨時筆記交給使用者核對）：

- **因果與伏筆台帳**：事件起因、當下用途、留下物、預定或可能回收點、是否已變形、是否已完成；允許標記「無遠期回收，純生活記憶」。
- **人物狀態台帳**：每名主要人物在每一篇進出時的境界、傷勢、能力、武器、關係、知情、責任與目前最強欲望。
- **篇章重量與節奏台帳**：每個故事屬於「純生活片段／有局部意義的事件／延遲發酵的伏筆／大篇主鏈」哪一級、預計篇幅、時間連接模式、主視角、核心問題、情緒強度，避免連續數篇使用同一種高潮或結尾。

### 四種時間連接模式

- **模式A：連續N篇**——單一危機持續升高、人物無法合理離場，每篇必須改變問題，不得只重複受困、追殺或辯論。
- **模式B：不連續案件鏈**——每一案能獨立成立，中間可隔時間與其他主線，但共享物件、手法、勢力或關係累積；總控要記錄每案留下什麼、下一案使用哪一項，不能只靠相同人物硬稱系列。
- **模式C：當下結束，後續才發酵**——事件表面已結束，真正後果在較晚時期出現。
- **模式D：只留生活記憶**——事件不服務陰謀或升級，只在人物之後的稱呼、習慣、笑話與相處中留下痕跡，價值是讓讀者相信角色共同生活過。

### 場景轉場七問（批准下一篇／下一章前自問）

1. 上一篇結束後，人物最自然會先做什麼？
2. 傷勢、資源、任務與情緒是否允許立刻進入新事件？
3. 新事件為何在此時找上這些人？
4. 前一篇的餘波是否至少在行為或環境中被承認？
5. 若時間跳躍，中間發生了什麼，正文需要寫、概述還是完全可省？
6. 讀者是否能感覺人物在章外仍繼續生活？
7. 轉換後的調性是刻意呼吸，還是無意中切斷張力？

如果新篇只能靠「某天突然收到任務」啟動，應優先尋找更自然的接口：前案留下的物件、傷者、目擊者、制度回應、敵方反制、生活責任或人物主動選擇。

### 全書節奏配置六要素（不能只有升高）

高壓連續篇、中篇案件、短冒險、修煉與工作日常、關係呼吸、戰後餘波——重大篇章之前要有足夠生活讓讀者知道角色可能失去什麼，之後要有餘波讓代價不被下一次冒險沖掉；但呼吸篇不能機械地固定插在每場戰鬥後，要依人物身體、情緒與世界局勢決定。

## 何時可以跳過流程

- 單純查詢設定內容、不產出新劇情或正文：直接讀 `docs/` 對應檔案即可，不需要呼叫任何 agent。
- 只是想要腦力激盪、還沒打算定案：只呼叫 `jie-creative` 即可，不必自動觸發後續審查。
- 使用者已經給了完整、明確核准的大綱，且只是要落筆：可以跳過 `jie-creative` 與 `jie-chapter-editor`，直接呼叫 `jie-writer` 模式一，但寫完後仍建議跑最終審查三件套。
- 使用者要處理已經存在的正文（含 Codex 產出）：改走上方「標準流程 B」，不套用標準流程 A。
